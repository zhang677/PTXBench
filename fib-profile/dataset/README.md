# PTXBench evaluator dataset subset

This directory contains the five definitions and five workload rows selected by
`../../multiturn/tests/{cuda,triton}`. It preserves the source
dataset layout so `TraceSet.from_path()` can load it. The complete dataset is on [huggingface](https://huggingface.co/collections/Genghan/ptxbench-qwen36-27b-sft-series).

Each workload file contains only the UUID selected by
the corresponding evaluator test. The two MHA backward rows reference the
safetensors files expected under `blob/workloads/attention/`. These large files
are intentionally not tracked in Git; generate them before running the backward tests,
or use `FIB_DATASET_MODE=bundled` during container creation to prepare them at startup.
The other three workloads generate their inputs and do not require blobs. The
evaluator tests submit their own solutions, so this subset contains no
`solutions/` directory.

## Generate the two MHA backward blobs

From the repository root, activate a CUDA 13 Python environment with PyTorch
2.12.1+cu130 (matching `entrypoint.sh`), cuDNN Python frontend 1.21.0, and
`safetensors` 0.8.0. Then run:

```bash
cd fib-profile
env LD_LIBRARY_PATH= python dataset/generate_blobs.py
```

Clearing `LD_LIBRARY_PATH` for this command avoids loading a different system CUDA
runtime alongside the environment's CUDA runtime.

The script can also run inside the `fib-profile` container after
`entrypoint.sh` has installed `/workspace/acc`, provided that environment has
the versions listed above:

```bash
docker exec fib-profile bash -lc 'source /workspace/acc/bin/activate && env LD_LIBRARY_PATH= python /workspace/dataset/generate_blobs.py'
```

The entrypoint pins Torch 2.12.1+cu130; cuDNN frontend and `safetensors` are
resolved from the bench's dependency requirements rather than pinned to these
exact versions. The script checks a GPU-specific expected SHA-256 before installing
each generated blob, so a different environment cannot silently substitute
unrecognized inputs.

The container launcher defaults to `FIB_DATASET_MODE=existing`, which uses the
mounted dataset without running this generator. For the bundled subset, set
`FIB_DATASET_MODE=bundled` when running `scripts/run_container.sh`; the entrypoint
then generates or verifies both blobs after installing the runtime, before
starting the service. It selects a cool device from `FIB_DEVICES` using the
service's UUID-based temperature check. Manual generation accepts
`--device cuda:1` to select another CUDA device.

For an existing dataset, set `HOST_DATASET_DIR=/absolute/path/to/dataset` and
leave `FIB_DATASET_MODE=existing`. That dataset must contain `definitions/`,
`workloads/`, and any blobs referenced by its workloads; it does not need
`generate_blobs.py`. See [container setup](../scripts/README.md) for examples.

The script reads the two workload rows, draws BF16 Q/K/V tensors from a seeded
normal distribution, computes O and log-sum-exp L with cuDNN SDPA forward,
and writes the safetensors files at the paths named by the workload rows.
The upstream gradient dO is generated by the evaluator. Existing blobs are
verified and skipped. A newly generated blob is installed only when its
SHA-256 matches the corresponding value below for the generating GPU. B200
uses the B200 values; the original values remain the default for other GPUs.
Existing files matching either published variant are valid on either GPU and
are left unchanged. An unknown checksum is always an error.

| Workload | H100 SHA-256 | B200 SHA-256 |
| --- | --- | --- |
| `mha_bwd_d128` | `c13f08ac9488481cecfb4a119235a6fdd05bb1f36de0acaa32445d2982dbd46b` | `d57de4d25ecbd180f55ba8ea41f57cb98f21b83f308047b153f6f2a65091ec83` |
| `mha_bwd_d128_causal` | `a2f25c87a1a20bc01a00cbc6e9db8677c3f5d80615a3ff6e548b792798a1b794` | `77541ccc959a00072446bb725b8c0498a09991b3e44e3f609c5e0843cf7bbabf` |

GPU-seeded `normal_` generation is not guaranteed to be bitwise identical across
GPU architectures: its CUDA launch geometry affects how RNG streams map to
tensor elements. H100 and B200 produce different Q/K/V with this generator;
the difference is not just cuDNN rounding in O/L. The workload shapes, seeds,
and UUIDs stay the same, but the input tensors differ between these two variants.
Keep the generation GPU and blob hashes with experiment results when comparing runs.

On 2026-10-11, fresh generation of both matching checksums and subsequent
verification of the existing blobs passed on a leased NVIDIA H100 80GB HBM3
using Torch 2.12.1+cu130, cuDNN Python frontend 1.21.0, `safetensors` 0.8.0,
cuDNN 9.20.0, and driver 580.126.20. The environment used the entrypoint's
package installation pins. Fresh generation on Modal H100 also reproduced both
original hashes. Fresh generation on Modal B200 and catalyst-fleet1 B200
reproduced the two B200 hashes with the same package versions; full per-tensor
hashes of Q/K/V/O/L matched between both B200 machines, and verification of
existing B200 blobs passed. Generation on another GPU or runtime may fail
checksum validation; mismatching blobs are never installed.
